# Feuille de route

Ce document liste ce qui est **envisagé**, pas engagé sur une date précise. Pour ce qui manque déjà aujourd'hui de façon plus factuelle, voir [USER_GUIDE.md](USER_GUIDE.md#ce-qui-nest-pas-encore-implémenté).

## Envisagé

- **Fournisseur de signature externe** (Yousign, DocuSeal...) pour un niveau de signature électronique renforcé (eIDAS "avancée"/"qualifiée"), en plus de la signature à l'écran actuelle (niveau "simple"). Le point d'extension existe déjà dans le code (`Provider\SignatureProviderInterface`) — seul `CanvasProvider` (signature à l'écran) est implémenté à ce jour ; brancher un prestataire externe n'exigerait pas de revoir l'architecture existante.
- **Étendre la couverture de tests automatisés aux contrôleurs `front/*.php`** eux-mêmes, actuellement testés manuellement via des scripts `curl` contre une vraie instance plutôt qu'en PHPUnit (risque réel de `Html::redirect()`/`exit()` interrompant le process de test si ces fichiers étaient inclus directement — cf. [TROUBLESHOOTING.md](TROUBLESHOOTING.md)). Une extraction plus poussée de leur logique vers des classes testables (à l'image de `Api\SignController` pour `front/sign.php`) réduirait ce point mort.
- **SonarCloud** en CI, en complément de PHPStan/phpcs déjà en place — non ajouté à ce jour, nécessite un compte externe et une décision du mainteneur sur l'outillage souhaité.
- **Passe d'amélioration UX/UI générale du plugin** — demande explicite de l'utilisateur, périmètre encore à définir précisément (revue à mener écran par écran : configuration, onglet Remise, page de signature, listes transverses...).
- **Rapprocher la gestion des gabarits de l'expérience du plugin** — aujourd'hui, `Template` (gabarits de remise) est un `CommonDropdown` standard, géré depuis Configuration > Intitulés, avec seulement un lien de renvoi (« Gérer les gabarits de ce type ») depuis les onglets de configuration du plugin. Demande de l'utilisateur : que ça se ressente comme un seul système cohérent plutôt que deux écrans distincts à garder synchronisés mentalement — par exemple en embarquant l'édition d'un gabarit directement dans l'onglet de configuration correspondant (Remise/Restitution/Don/Vente), plutôt qu'un simple lien vers l'écran séparé `front/template.form.php`. Techniquement, la donnée est déjà unique (une seule table `glpi_plugin_remise_templates`, pas de duplication) — le travail est donc côté UX/organisation des écrans, pas migration de données.
- **Fil d'Ariane (breadcrumb) ramenant directement au plugin depuis les écrans d'Intitulés** — actuellement, les intitulés du plugin (Gabarits de remise, Accessoires, Points de contrôle de maintenance) affichent un fil d'Ariane générique (`Accueil / Configuration / Intitulés`), sans lien retour vers le plugin lui-même. Objectif : `Accueil / Administration / Remise & Signature / ...`, cohérent avec l'emplacement réel du plugin dans le menu (Outils/Administration). À investiguer : comment `Html::header()`/le 3ᵉ paramètre `$sector` sont utilisés par les `front/*.php` de ce plugin par rapport aux `front/dropdown.php` génériques qui servent les pages d'Intitulés.
