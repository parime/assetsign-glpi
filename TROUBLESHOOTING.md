# Dépannage et notes techniques

Cette page documente les pièges et décisions non évidentes rencontrés en conditions réelles pendant le développement et la maintenance de ce plugin — elle s'adresse à qui reprend ou modifie le code, pas à l'utilisateur final (voir plutôt le [README](README.md)). Pour la structure du code et les tests, voir [ARCHITECTURE.md](ARCHITECTURE.md).

- **Namespace PSR-4** : `GlpiPlugin\Remise`, classes dans `src/GlpiPlugin/Remise/` (composer.json), conforme à la convention GLPI 11 pour les plugins modernes.
- **Isolation des erreurs dans les hooks** : `plugin_remise_item_assignment()` et `plugin_remise_item_pre_purge()` (`hook.php`) enveloppent tout appel dans un `try/catch (\Throwable)`, avec journalisation via `Toolbox::logInFile('remise', ...)` (fichier `files/_log/remise.log`). Ces fonctions sont appelées de manière synchrone par `CommonDBTM::add()`/`update()` (`Plugin::doHook()`) : sans ce garde-fou, une exception côté plugin (fournisseur de signature non implémenté, échec de génération PDF...) remonterait jusque dans la sauvegarde de l'item GLPI lui-même — un technicien qui réaffecte un simple ordinateur se prendrait une erreur sur *sa* sauvegarde à cause d'un problème qui ne concerne que le plugin.
- **Accès à `front/sign.php`** : connexion GLPI obligatoire, via `Glpi\Http\Firewall::addPluginStrategyForLegacyScripts(..., STRATEGY_AUTHENTICATED)` dans `setup.php` (explicite, alors que c'est déjà le comportement par défaut du pare-feu GLPI 11 — la ligne documente que c'est un choix assumé). Le contrôle d'identité fin (seul le bénéficiaire peut voir/signer *son* document, pas n'importe quel utilisateur connecté) est fait dans `SignController::assertCurrentUserIsBeneficiary()`, appelé par `show()`, `submit()` et le téléchargement du PDF. **Conséquence opérationnelle** : le bénéficiaire doit pouvoir se connecter à GLPI avec ses propres identifiants (compte AD synchronisé avec authentification LDAP, par exemple) — un compte GLPI qui existe uniquement pour la gestion de parc mais sans authentification possible bloquerait la signature.
- **CSRF** : GLPI valide automatiquement le jeton CSRF pour toute requête POST vers une page de plugin (`Hooks::CSRF_COMPLIANT`). Ne rappelez **jamais** `Session::checkCSRF()` vous-même dans un front controller : le jeton est à usage unique et serait déjà consommé, ce qui provoquerait un faux « Access denied ».
- **Cible de notification** : `NotificationTargetRemise` n'utilise **ni** `Notification::ITEM_USER` (bénéficiaire) **ni** `Notification::ITEM_TECH_IN_CHARGE` (technicien) : ces types natifs font un `INNER JOIN` sur `Profile_User` (`NotificationTarget::getProfileJoinCriteria()`) qui exige un profil GLPI actif dans l'entité — silencieusement sans erreur si absent. **Vérifié en conditions réelles** : `ITEM_TECH_IN_CHARGE` ne notifiait jamais le technicien dans l'environnement de test, malgré un profil actif en base, un e-mail configuré et `users_id_tech` correctement rempli. Deux types personnalisés (`TARGET_BENEFICIARY`, `TARGET_TECHNICIAN`) notifient directement par e-mail via `addUserFieldByEmail()`, sans cette jointure. Ce n'est pas lié à la connexion requise pour signer : ça concerne uniquement l'envoi de l'e-mail par le moteur de notifications GLPI (beaucoup d'employés synchronisés depuis l'Active Directory ont un compte GLPI sans profil associé — et un technicien à profil restreint peut être dans le même cas).
- **Nom des Documents GLPI (`getDocumentTitle()`) ET contenu du PDF volontairement non traduits** : le PDF non signé est généré pendant le hook `item_add`/`item_update` (session du **technicien** qui fait l'affectation), le PDF signé pendant `submit()` de la page de signature (session du **bénéficiaire**). Utiliser `__()` pour le type ("Remise"/"Restitution"), les titres ou le type de matériel ferait donc dépendre la langue du **contenu du document** (pas seulement son nom de fichier) de qui a déclenché l'action — **constaté en conditions réelles** : un même PDF affichant un titre en anglais puis un intitulé en français juste en dessous. `getCanonicalTypeLabel()` et `getCanonicalItemtypeLabel()` fixent volontairement ces libellés dans une seule langue (français), indépendamment de `getTypes()`/`getTypeName()` natif (qui restent traduits, à raison, pour tout ce qui est réellement propre à un utilisateur donné). Un PDF archivé est un document unique, potentiellement relu par plusieurs personnes à des dates différentes — ce n'est pas un contenu qui doit varier selon qui l'a généré.
- **E-mails multilingues** : chaque gabarit de notification a deux traductions (`NotificationTemplateTranslation`) — `language => ''` (française, universelle) et `language => 'en_GB'`. GLPI choisit automatiquement celle qui correspond à la langue du compte GLPI du destinataire, sinon retombe sur la française. Testé en direct : un utilisateur en `fr_FR` et un utilisateur en `en_GB` affectés au même type de matériel reçoivent chacun l'e-mail dans leur langue.
- **Document::add()** attend le fichier physique dans `GLPI_TMP_DIR` (entrée `_filename`), pas dans un dossier arbitraire.
- **Mode de notification** : la valeur exacte est `Notification_NotificationTemplate::MODE_MAIL` (= la chaîne `'mailing'`, pas `'mail'`).
- **Commandes console de plugin** : GLPI les découvre en scannant récursivement `src/` (et `inc/`) à la recherche de tout fichier se terminant par `Command.php` dont la classe étend `Symfony\Component\Console\Command\Command` — aucun enregistrement dans `setup.php` n'est nécessaire. Seule contrainte : le nom de la commande doit commencer par `plugins:remise:`.
- **Traductions dans les gabarits Twig** : la fonction Twig est `__('texte', 'remise')` (une fonction, enregistrée par `I18nExtension`), pas un filtre `|trans` — GLPI ne fournit pas ce filtre, l'utiliser fait planter le rendu (`Twig\Error\SyntaxError`).
- **Menu d'administration (`Hooks::MENU_TOADD`)** : la documentation du hook décrit un format `['types' => [...], 'icon' => '...']` par catégorie — **ce n'est pas ce que le code lit réellement**. Le code attend une liste PLATE de classes directement : `['admin' => [Remise::class, Template::class, Config::class]]`. Suivre la documentation littéralement casse le menu sur **toutes** les pages GLPI, avec l'erreur `Twig\Error\RuntimeError: "Class name must be a valid object or a string"`. L'icône s'auto-détecte depuis la première classe listée qui implémente `getIcon()`.
- **Actifs personnalisés et `plugin_init_<plugin>()`** : `Glpi\Asset\AssetDefinitionManager::getInstance()->getDefinitions()` renvoie **toujours un tableau vide** quand on l'appelle depuis `plugin_init_remise()`. Cause : l'ordre des listeners de boot de GLPI exécute `InitializePlugins` (qui déclenche `plugin_init_<plugin>()`) **avant** `CustomObjectsBoot` (qui peuple réellement le cache des définitions). Contournement utilisé ici (`Config::getAllManageableItemtypes()`) : une requête SQL directe sur `glpi_assets_assetdefinitions`, disponible dès la connexion DB, bien avant `InitializePlugins`.
- **Héritage de configuration par entité (`Config::getForEntity()`)** : ne se limite pas à "l'entité elle-même, sinon directement la racine" — la config effective est celle de l'ancêtre **le plus proche** qui en possède une, calculée via `getAncestorsOf('glpi_entities', $entities_id)` puis en gardant, parmi les ancêtres ayant une ligne de config, celui dont le champ `level` de `glpi_entities` est le plus élevé (= le plus profond/proche). Ainsi, une organisation à plusieurs niveaux (Racine > Région > Site) peut configurer le plugin sur une entité intermédiaire et voir ce réglage s'appliquer à ses entités enfants sans config propre, même si la racine n'a pas non plus de config.
- **Type "Échange" retiré** : `Remise::TYPE_EXCHANGE` (valeur `2`) et le réglage `sign_on_exchange` ont été supprimés — un transfert direct entre deux personnes crée désormais une remise normale (`TYPE_HANDOVER`) au nouveau détenteur, comme une réaffectation classique. La valeur `2` reste volontairement commentée comme inutilisée pour ne pas être réutilisée par erreur pour autre chose. Montée de version : `Template::install()` désactive (`is_active = 0`, sans supprimer) tout gabarit existant de type `2` sur une installation déjà en place.
- **`runReminders()`/`runExpiration()` résolvent la config PAR REMISE, pas globalement** : chaque remise résout sa propre config via `Config::getForEntity((int) $remise->fields['entities_id'])` à l'intérieur de la boucle, plutôt qu'une seule fois avant la boucle — sans quoi la config d'une entité non-racine n'avait jamais d'effet pour les tâches automatiques. Conséquence technique pour `runExpiration()` : le filtre de délai ne peut plus se faire dans la clause SQL `WHERE` (chaque entité a potentiellement sa propre durée de validité) — il se fait en PHP, ligne par ligne, après récupération de toutes les remises encore ouvertes.
- **Cartes de tableau de bord (`CardProvider`) restreintes à l'entité active** : `countByStatus()` ajoute `getEntitiesRestrictCriteria(Remise::getTable(), '', '', true)` à la clause `WHERE`, exactement comme `Glpi\Dashboard\Provider::bigNumberItem()` le fait nativement pour tout itemtype possédant un champ `entities_id`. Sans ça, les cartes comptaient les remises de tout GLPI sans tenir compte de l'entité active sélectionnée.
- **Logo imposé aux entités enfants (`logo_force_children`) : résolution séparée de l'héritage habituel de la config** : `Config::getForEntity()` n'hérite le logo (comme le reste des réglages) que pour une entité qui n'a AUCUNE ligne de config propre — une entité qui a déjà personnalisé autre chose (son e-mail d'expéditeur, par exemple) resterait sinon bloquée sur son propre logo, sans qu'une entité parente puisse malgré tout lui imposer le sien. `Config::getEffectiveLogoDocumentId()` calcule donc la valeur affichée/utilisée séparément : elle remonte tous les ancêtres (`getAncestorsOf()`, pas seulement le parent direct — une entité petite-enfant d'une entité qui impose hérite donc aussi) à la recherche de ceux ayant `logo_force_children = 1`, et retient celui de niveau le plus profond (le plus proche) en cas d'imposition sur plusieurs branches différentes. Une entité qui impose elle-même un logo à ses propres entités enfants n'est pas pour autant immunisée contre l'imposition d'un de ses ancêtres : la règle « ancêtre imposant le plus proche gagne » s'applique uniformément, y compris à elle-même. **Vérifié en conditions réelles** sur une hiérarchie à 3 niveaux (A impose logo1 → B a sa propre config avec logo2 mais pas d'imposition → C, petite-enfant de A sans config propre) : B et C affichent bien logo1, pas logo2 ; et avec D (entité enfant de B, imposant logo3) et E (entité enfant de D), E affiche logo3 (l'imposition de D, plus proche, l'emporte sur celle de A), tandis que D lui-même affiche logo1 (imposé par A, son propre ancêtre le plus proche).
- **Passe de revue de code (réutilisation, code mort, efficacité, architecture)** : le code a été relu en entier après plusieurs mois de développement continu, jamais revu indépendamment jusque-là. Résultat, appliqué et vérifié par une nouvelle exécution complète des tests et des flux réels (affectation → signature → restitution → tableau de bord) :
  - Code mort supprimé : `Token::invalidate()`, `Config::getDefault()`, `Remise::getConfig()`, les états `viewed`/`signed`/`refused` de `SignatureCallbackResult` (jamais produits ni consommés, seul `ignored` l'était réellement — cette classe a depuis été retirée entièrement, cf. plus bas), deux variables `$newId` jamais lues (`front/accessory.form.php`, `front/template.form.php`), et l'enregistrement `add_javascript` vide dans `setup.php` (le script de signature est chargé directement en balise `<script>` par `sign_page.html.twig`, pas par ce hook).
  - **`Signature::getForRemise()` avait aussi été supprimé ici comme code mort, à tort** : sa suppression a révélé que la preuve de signature (adresse IP, empreinte du document...) collectée par `Signature::recordProof()` à chaque signature n'était affichée strictement **nulle part** — pas un oubli de nettoyage mais un vrai manque fonctionnel, puisque c'est la valeur même d'une preuve de signature électronique. Remis en place et câblé : la fiche d'une remise signée (`remise_form.html.twig`) affiche désormais signataire, IP, navigateur et empreinte SHA-256 via `Signature::getForRemise()`, appelé depuis `Remise::showForm()` uniquement quand `status === STATUS_SIGNED`. Vérifié en conditions réelles : signature avec IP/user-agent factices, preuve retrouvée en base, puis affichage confirmé sur la vraie page `remise.form.php` (les 4 informations apparaissent bien dans le HTML rendu).
  - Duplication réduite : `Remise::STATUSES_AWAITING_SIGNATURE` (envoyé/consulté) et `Remise::STATUSES_STILL_EDITABLE` (tout ce qui précède la signature) remplacent le même couple/quadruplet de statuts recopié à 6 endroits différents (formulaire, relance manuelle, crons, `CardProvider`) ; `Remise::daysSince()` remplace le même calcul `floor((time() - strtotime(...)) / DAY_TIMESTAMP)` dupliqué dans `runReminders()`/`runExpiration()` ; `Config::pickRowOfClosestEntity()` factorise l'algorithme de résolution "ancêtre le plus proche parmi plusieurs candidats", jusque-là recopié à l'identique entre `getForEntity()` et `getEffectiveLogoDocumentId()` ; les 7 classes qui déclarent `$rightname` référencent maintenant `Profile::RIGHT_REMISE`/`RIGHT_CONFIG`/`RIGHT_TEMPLATE` plutôt que de recopier la chaîne littérale.
  - Efficacité : `runReminders()`/`runExpiration()` n'appellent plus `$remise->getFromDB($row['id'])` (une requête `SELECT *` redondante, la ligne complète étant déjà en main) et mettent en cache `Config::getForEntity()` par entité le temps de la boucle (plusieurs remises partagent souvent la même entité) ; `Config::getEffectiveLogoDocumentId()` accepte un logo déjà connu en fallback optionnel, évitant à `showConfigForm()` de rappeler `getForEntity()` une deuxième fois pour la même entité.
  - Conservé intentionnellement malgré des références nulles ou faibles à cette date (documenté ici pour ne pas être re-signalé par erreur comme oubli) : `AbstractProvider::$providerConfig` — c'est l'infrastructure d'extensibilité pour un futur fournisseur externe asynchrone (Yousign/DocuSeal, cf. section "Ce qui n'est pas encore implémenté"), pas du code mort accidentel.
- **Action groupée "Relancer" (`Remise::getSpecificMassiveActions()`)** : suit le contrat standard `getSpecificMassiveActions()`/`showMassiveActionsSubForm()`/`processMassiveActionsForOneItemtype()` de `CommonDBTM`, exactement comme le cœur GLPI le fait pour toute autre action groupée — aucun mécanisme propre au plugin. `processMassiveActionsForOneItemtype()` rattrape le `RuntimeException` de `sendReminderNow()` (remise déjà signée/expirée) en `MassiveAction::ACTION_KO` plutôt que de laisser planter tout le lot : une sélection mélangeant des remises encore en attente et d'autres déjà traitées relance correctement les premières sans bloquer sur les secondes. **Vérifié en conditions réelles** avec un vrai objet `MassiveAction` construit au stade `process` (comme le fait `ajax/massiveaction.php`) : l'action apparaît bien dans `getSpecificMassiveActions()`, `reminder_count` s'incrémente après traitement, et une remise déjà signée est bien marquée KO sans exception.
- **Alerte de pré-expiration (`Remise::runExpiryWarnings()`, événement `expiring_soon`)** : mécanisme volontairement séparé de `runExpiration()` (cron/console propres, `remiseExpiryWarning`/`plugins:remise:warn-expiring`), suivant la même convention qu'un mécanisme par préoccupation déjà en place (`remiseReminders`/`remiseExpire`/`remiseCleanupTokens`) plutôt que de complexifier la boucle existante. N'est adressé qu'au technicien (`TARGET_TECHNICIAN`), pas au bénéficiaire qui reçoit déjà des relances périodiques sur la même fenêtre — l'envoyer aussi au bénéficiaire ferait doublon. Un champ dédié `expiry_warning_sent` (et non un simple recalcul à chaque exécution) évite de re-notifier à chaque passage du cron tant que la remise n'a pas changé d'état.
  - **Piège rencontré en l'implémentant, avec un impact plus large** : `Migration::addField($table, $field, $type, $options)` ne construit une clause `DEFAULT` (à partir de `$options['value']`) que pour les types "logiques" reconnus par `Migration::fieldFormat()` (`bool`, `integer`, `str`, `text`...) ; un type SQL passé tel quel (`'tinyint'`, `'int unsigned'`) tombe dans le `default:` du switch, qui renvoie le type **sans aucun `DEFAULT` ni `NOT NULL`** — `$options['value']` est alors silencieusement ignoré pour la définition de colonne (il ne sert que pour l'option `update`, distincte). Conséquence concrète : une colonne ainsi ajoutée est NULL par défaut pour toute nouvelle ligne qui ne la renseigne pas explicitement, et une clause `WHERE colonne => 0` n'égale jamais une valeur NULL en SQL — `runExpiryWarnings()` ne trouvait donc silencieusement aucune remise à traiter (`expiry_warning_sent` valant NULL, pas 0, sur les remises créées après la migration). Ce même piège affectait déjà `logo_force_children` (ajouté plus tôt avec le type brut `'tinyint'`), sans conséquence visible jusqu'ici uniquement parce que `Config::upsertForEntity()` renseigne toujours explicitement ce champ. Corrigé : les trois `addField()` concernés utilisent désormais `'bool'`/`'integer'` plutôt que le type SQL brut.
- **Titre de la page de signature volontairement DIFFÉRENT du titre du PDF** : `front/sign.php` construisait jusqu'ici le `page_title` de `sign_page.html.twig` à partir de `Remise::getPdfHeadings()` — fixé en français à dessein pour le PDF (contenu archivé, cf. plus haut), mais cette page-ci est une interface consultée en direct par le bénéficiaire, déjà entièrement traduite via `__()` partout ailleurs (titre du navigateur, `<h1>`, tous les libellés). Résultat avant correctif : un bénéficiaire en session anglaise voyait toute la page traduite sauf son propre titre principal, resté en français. Deux nouvelles chaînes dédiées à cette page (`Signature de remise de matériel` / `Signature de restitution de matériel`) remplacent l'emprunt au titre du PDF. **Vérifié en conditions réelles** avec une session bénéficiaire `en_GB` : le HTML rendu contient bien `"Equipment handover signature"`, plus aucune trace du titre français fixe.
- **Constantes nommées pour deux seuils de `Token.php`** : le nombre maximum de tentatives d'accès avant désactivation par sécurité (`MAX_ATTEMPTS = 20`) et la durée de rétention avant purge des jetons invalides (`CLEANUP_RETENTION_DAYS = 90`) étaient des nombres magiques recopiés en dur, ce dernier dupliqué une deuxième fois en toutes lettres dans la description du CronTask (`hook.php`). Nommés en constantes de classe (`CLEANUP_RETENTION_DAYS` rendue `public` exprès pour que `hook.php` la référence au lieu de recopier "90 jours" séparément). Volontairement de simples constantes plutôt que des réglages par entité : ce sont des paramètres de sécurité/rétention technique, pas des choix qui varient légitimement d'une société à l'autre comme le sont les délais de relance ou la durée de validité du lien.
- **Quatre chaînes de traduction orphelines nettoyées** : `"Échange"`, `"Fiche d'échange de matériel"`, `"Matériel échangé"` et `"Signature lors d'un échange direct..."` restaient dans `locales/fr_FR.po`/`en_GB.po` après le retrait du type "Échange" (`Remise::TYPE_EXCHANGE`) — le code ne les produit plus nulle part, mais le nettoyage du code n'avait pas touché les fichiers de traduction. Retirées.
- **Bug réel signalé par un premier usage humain réel : chemins codés en dur depuis la racine du domaine** : `remise_form.html.twig`, `config_form.html.twig`, `remise_tab.html.twig`, `template_form.html.twig` et surtout `sign_page.html.twig` construisaient leurs `action`/`src`/`href` en `/plugins/remise/...` fixe — correct uniquement si GLPI est installé à la racine du domaine, pas dans un sous-dossier (ex. `/glpi/`), pourtant un cas d'installation très courant. Conséquence concrète, remontée par un test réel (souris en main, pas un script) : sur la page de signature, **impossible de dessiner et aperçu du PDF vide**, parce que les scripts `pdf.min.js`/`signature_pad.umd.min.js`/`pdf.worker.min.js` échouaient silencieusement à charger. Toute la session de tests Docker précédente n'avait jamais détecté ce problème car l'instance de test tournait justement à la racine (`http://localhost:8091/`). Corrigé en généralisant l'usage de `{{ config('root_doc') }}` côté Twig et de `$CFG_GLPI['root_doc']` côté PHP (le même réflexe que le cœur GLPI applique partout, cf. `Auth.php`, `Central.php`...) ; pour `sign.js` (fichier statique, pas un template Twig), le chemin du worker PDF.js est désormais lu depuis `window.REMISE_ROOT_DOC`, injecté par `sign_page.html.twig`. **Vérifié en conditions réelles** en simulant `$CFG_GLPI['root_doc'] = '/glpi'` : les URL générées (formulaires, scripts, lien du tableau de bord) sont bien préfixées, sans régression sur une installation à la racine (`root_doc` y vaut `''`, donc concaténation neutre).
- **La vraie cause de "impossible de signer" : GLPI 11 exige un dossier `public/` dans chaque plugin pour ses fichiers statiques.** Le correctif `root_doc` ci-dessus était réel et nécessaire (installation en sous-dossier), mais **pas suffisant** : sur le serveur réel de l'utilisateur (installé à la racine du domaine, donc `root_doc` vide), les fichiers `pdf.min.js`/`sign.js`/`signature_pad.umd.min.js`/`remise.css` continuaient de renvoyer une erreur 404 après le correctif. Cause identifiée via les outils de développement du navigateur (onglet Réseau) fournis par l'utilisateur, puis confirmée par la documentation officielle GLPI ([guide de migration 11.0](https://glpi-developer-documentation.readthedocs.io/en/master/upgradeguides/glpi-11.0.html)) : depuis GLPI 11, le `DocumentRoot` du serveur web pointe obligatoirement sur `glpi/public/` (plus une option comme en GLPI 10) ; toute ressource statique d'un plugin (JS, CSS, images) doit donc être placée physiquement dans un sous-dossier **`public/`** à l'intérieur du plugin (`plugins/remise/public/js/...`, `plugins/remise/public/css/...`), alors que son URL reste inchangée et **ne contient pas** "public" (`/plugins/remise/js/...`). C'est GLPI lui-même (routeur `public/index.php`) qui fait la correspondance en interne. Sans ce dossier, même le CSS enregistré via le mécanisme natif `Hooks::ADD_CSS` de GLPI (`Html::css()`, aucun code du plugin en cause) renvoyait 404 — la preuve que ce n'était pas un bug spécifique à ce plugin mais une règle GLPI 11 non suivie. Corrigé en déplaçant `js/` et `css/` vers `public/js/` et `public/css/` (aucun changement d'URL ni de `setup.php` nécessaire, `Hooks::ADD_CSS`/le `<script src>` gardent exactement les mêmes chemins). **Vérifié en conditions réelles** : les 4 ressources qui renvoyaient 404 renvoient désormais 200 avec le contenu attendu (tailles de fichiers identiques à celles constatées sur le serveur de l'utilisateur).
- **Texte par défaut pré-rempli pour un nouveau gabarit** : jusqu'ici, seul le tout premier gabarit semé automatiquement à l'installation avait un texte de conditions générales/charte non vide — un gabarit créé ensuite par un administrateur depuis l'interface partait de champs entièrement vides, avec un risque réel de fiche de remise sans aucune condition affichée au bénéficiaire (constaté en conditions réelles). `Template::getDefaultContentFor()` centralise désormais ce texte par défaut, réutilisé à la fois par le seed d'installation et par le formulaire d'un nouveau gabarit — librement modifiable ou effaçable par l'administrateur, ce n'est qu'une valeur de départ. **Formule "Je soussigné(e)" retirée** de ce texte par défaut (Remise/Restitution/Don/Vente), remplacée par une formulation directe ("Je reconnais..."). **Important** : cette constante n'affecte que les *nouveaux* gabarits créés à partir de maintenant — un gabarit déjà existant en base garde son propre texte tel quel (stocké dans `glpi_plugin_remise_templates.content`, jamais réécrit automatiquement) ; pour appliquer ce changement à un gabarit déjà créé, il faut éditer son texte manuellement depuis **Administration > Remise & signature > Gabarits de remise**.
- **Moteur multi-type (`src/GlpiPlugin/Remise/Workflow/`)** : `WorkflowTypeInterface` + `WorkflowTypeRegistry` remplacent les `match($type)` autrefois dispersés dans `Remise.php`/`Template.php` (libellés, titres de PDF, texte par défaut). `Remise::getTypes()`/`getPdfHeadings()`/`getCanonicalTypeLabel()` et `Template::getDefaultContentFor()` ne sont plus que de simples délégations vers le registre — un futur type de fiche (Don, Vente...) s'ajoutera en créant une nouvelle classe + une ligne d'enregistrement dans `plugin_init_remise()` (`setup.php`), sans modifier ces classes partagées. `WorkflowTypeRegistry::get()` lève une `RuntimeException` sur un type inconnu plutôt que de se rabattre silencieusement sur "Remise" — un type invalide en base est un vrai bug qui doit remonter, pas être masqué.
- **CGU/Charte activables indépendamment (`Template::include_content`/`include_charter`)** : migration avec valeur par défaut `1` sur les **deux** colonnes — un défaut à `0` aurait fait disparaître silencieusement les mentions légales de tous les gabarits déjà en production dès le prochain PDF généré. La section Charte reste un bloc unique dans `handover.html.twig` (texte **et** lien `charter_url` de la configuration d'entité sous la même case à cocher) : désactiver `include_charter` masque tout le bloc, pas seulement le texte du gabarit.
- **Objet des e-mails adapté au type sans multiplier les notifications** : plutôt qu'une notification par (type × événement), le tag déjà existant `##remise.type##` (résolu par `NotificationTargetRemise::addDataForTemplate()`) est simplement réutilisé dans le sujet et le corps de chaque gabarit d'e-mail — un seul jeu de 5 notifications (`new`/`reminder`/`signed`/`expired`/`expiring_soon`) fonctionne pour tous les types actuels et à venir. Contenu extrait dans `Notification\DefaultNotificationContent::forEvent()`, `NotificationTargetRemise::install()` devenant une pure orchestration (création/idempotence/ciblage) sans chaîne HTML en dur. **Piège rencontré** : le sous-namespace `GlpiPlugin\Remise\Notification\` entre en collision avec la classe cœur `\Notification` déjà importée (`use Notification;`) dans ce même fichier — une référence relative `Notification\DefaultNotificationContent` se résolvait contre la classe importée, pas contre le sous-namespace (`Attempted to load class "DefaultNotificationContent" from namespace "Notification"`, révélé uniquement à l'exécution réelle de `plugin:install --force`, jamais par le simple lint). Corrigé avec un `use GlpiPlugin\Remise\Notification\DefaultNotificationContent;` explicite. **Modèle de notification propre à une organisation en particulier** : à appliquer manuellement sur l'instance concernée (`NotificationTemplateTranslation::update()` ou l'écran natif Configuration > Notifications), jamais committé dans ce dépôt public — le plugin distribué reste 100% générique.
- **Historique natif contourné par les mises à jour SQL en masse** : `Remise::cancelPendingRemisesFor()` (annulation automatique lors d'une réaffectation) écrit directement en SQL plutôt que via `update()`, pour éviter un aller-retour complet par remise dans une boucle — mais cela signifie que l'historique natif de `CommonDBTM` (déclenché par `update()`) n'enregistre jamais cette annulation. Un appel explicite à `Log::history($id, Remise::class, ['0', '', $message], 0, Log::HISTORY_LOG_SIMPLE_MESSAGE)` (même convention que `Cartridge.php` dans le cœur GLPI) reconstitue cette trace. `Remise::cancelRequest()` (annulation manuelle, bouton ou action groupée) passe elle par `update()` : l'historique natif la capture déjà, aucun appel explicite nécessaire.
- **"Gestion des fiches" (`Hooks::MENU_TOADD`)** : ce plugin n'ajoutait volontairement aucune entrée de menu latérale (onglet par matériel + widgets de tableau de bord suffisaient) — ce choix ne tenait plus dès qu'il fallait un écran unique listant toutes les remises tous matériels confondus, avec téléchargement direct du PDF et annulation. Réutilise `Search::show(Remise::class)` tel quel (`front/remise.php`, déjà existant) : aucun nouvel écran à construire, seulement deux colonnes `getSearchOptions()` supplémentaires (`document_id_unsigned`/`document_id_signed`, `nosearch: true` car un ID de Document interne n'a aucun sens à filtrer) rendues en lien de téléchargement via `getSpecificValueToDisplay()` et `front/document.send.php`.
- **Don et Vente : deux canaux de création, manuel ET automatique par État** : à l'origine, seul un formulaire manuel sur l'onglet Remise (`remise_tab.html.twig`, via `Remise::createManual()`) permettait de créer un Don/une Vente — rien dans GLPI ne signale automatiquement "ce matériel est donné/vendu". `Remise::MANUALLY_CREATABLE_TYPES` restreint volontairement les types acceptés par ce canal (Don, Vente) : sans cette liste blanche, rien n'empêcherait un appel direct de créer une Remise/Restitution par ce chemin, contournant la déduplication faite par `cancelPendingRemisesFor()` (spécifique au déclenchement automatique) et laissant potentiellement des fiches orphelines. Depuis la Phase 3, `Config::getDonationStates()`/`getVenteStates()` (même forme JSON que `getHandoverStates()`/`getReturnStates()`) permettent en plus un déclenchement automatique par changement d'État, câblé dans `Remise::handleStateBasedTrigger()` de façon symétrique aux deux blocs déjà là pour Remise/Restitution — `createRemise()` étant déjà générique, aucune modification n'y était nécessaire. Une Vente ainsi créée automatiquement n'a délibérément aucune ligne `VenteDetails` (prix inconnu à cet instant) : `handover.html.twig` masque déjà la section correspondante quand `vente_price is null`. `Remise::updateVenteDetails()` (garde `type === TYPE_VENTE` et `isStillEditable()`) permet de renseigner prix/date après coup et régénère le PDF non signé, via `VenteDetails::upsertForRemise()` (créer-ou-mettre-à-jour, contrairement à `createForRemise()` qui suppose l'absence de ligne). `TYPE_DON`/`TYPE_VENTE` valent `3`/`4` — jamais `2`, valeur documentée comme définitivement retirée (ancien type "Échange").
- **Vente : le prix/la date sont les SEULES données réellement nouvelles** : "vendeur" et "acheteur" ne sont pas des colonnes ajoutées — ce sont déjà `users_id_tech`/`users_id` sur `Remise`, réutilisés tels quels. Seuls le prix et la date de vente vont dans une table dédiée 1-vers-1 (`glpi_plugin_remise_ventedetails`, `VenteDetails.php`) — exactement le point d'extension "table dédiée par type" prévu (mais jamais utilisé) depuis la Phase 1. **Contrainte assumée, pas encore un vrai besoin métier vérifié** : l'acheteur doit être un compte GLPI existant, car `Api\SignController::assertCurrentUserIsBeneficiary()` exige que le signataire connecté corresponde exactement à `remise.users_id` — vendre à un tiers sans aucun compte GLPI demanderait un mécanisme de signature par lien e-mail sans connexion, qui contredirait le choix assumé ailleurs dans ce projet (connexion obligatoire, cf. `setup.php`).
- **État des lieux visuel : aucun équivalent natif GLPI, tout est construit from scratch** — confirmé par recherche dans le cœur GLPI avant de commencer : le glisser-déposer de `Rack`/`DCRoom` s'accroche à une grille, pas à des coordonnées libres sur une photo, et `Document`/`Document_Item` n'a pas de colonne d'extension pour stocker des métadonnées de position. `glpi_plugin_remise_damagemarkers` stocke des coordonnées en **pourcentage** (`x_percent`/`y_percent`), pas en pixels : condition nécessaire pour repositionner correctement le même repère à l'écran (taille variable) et dans le PDF (taille de rendu différente). Les 3 images de référence (`public/images/damage-views/arriere.jpg`, `avant.jpg`, `dessous.jpg` — de vraies photos fournies par l'utilisateur, pas des croquis maison ; une première version avec 8 vues génériques dessinées à la main a été remplacée par ces 3 vraies vues, les seules réellement fournies) sont encodées en data URI pour le PDF — même raison que le logo (`getLogoDataUri()`) : Dompdf tourne chrooté sur `GLPI_DOC_DIR`, ces images vivent hors de ce dossier. Le type MIME de la data URI est déterminé depuis l'extension réelle du fichier (`jpg`/`jpeg` → `image/jpeg`, `png`, `svg`) plutôt que codé en dur sur `image/svg+xml` — piège rencontré au passage aux vraies photos JPEG, qui s'affichaient sinon comme des images cassées dans le PDF malgré des données correctement encodées. Les 3 vues s'affichent côte à côte dans le PDF (`.damage-pdf-col` en `display: inline-block`, largeur en **pourcentage** — `31%` + marges `3.5%` — plutôt qu'en pixels fixes, pour s'adapter aussi bien à la pleine largeur d'une page PDF qu'à la colonne plus étroite de l'aperçu en direct sur les pages de configuration/gabarit) — chaque colonne regroupe son image, son libellé et la liste de ses repères décrits, pour rester autonome même si Dompdf doit la faire passer sur la page suivante (`page-break-inside: avoid`). **Deux pièges rencontrés en mettant ce côte-à-côte en place** : (1) une première tentative avec des largeurs en pixels fixes fonctionnait dans le vrai PDF (page pleine largeur) mais empilait les 3 vues verticalement dans l'aperçu en direct, dont la colonne (`template_form.html.twig`/`config_form.html.twig`, layout deux colonnes) est nettement plus étroite qu'une page PDF — les pourcentages, qui s'adaptent à la largeur réelle du conteneur, réglent le problème pour les deux contextes à la fois ; (2) une tentative intermédiaire avec Flexbox (`display: flex`, colonnes à largeur égale) semblait la solution la plus propre en CSS moderne, mais le moteur de rendu de Dompdf ne la gère pas correctement ici : chaque vue occupait toute la largeur de page et finissait seule sur sa propre page — **constaté en conditions réelles** sur un vrai PDF généré, pas une supposition. Le support Flexbox de Dompdf reste donc à éviter pour ce genre de mise en page, au profit du couple `display: inline-block` + largeurs en pourcentage, plus ancien mais nettement plus fiable dans ce moteur. Un conteneur `.damage-pdf-views { font-size: 0; }` (largeurs des colonnes redéfinies à `font-size: 11px`) élimine l'espace blanc inter-éléments propre à `inline-block` qui aurait sinon fait déborder les 3 colonnes au-delà de 100% de la largeur disponible. **Piège rencontré, avec la même cause que celui déjà documenté pour le titre canonique du type de fiche** : `DamageMarker::getViewLabels()` (traduit via `__()`) est utilisée à la fois par l'écran d'annotation en direct (`remise_form.html.twig`, où la traduction selon la session du technicien est légitime) et — jusqu'à ce correctif — par le PDF lui-même, où elle produisait un libellé de vue dans la langue de la session de qui a déclenché la génération (technicien à l'affectation, bénéficiaire à la signature), constaté en conditions réelles avec des libellés anglais dans un PDF par ailleurs entièrement en français. `DamageMarker::getCanonicalViewLabels()` (chaînes fixes, sans `__()`) est désormais utilisée par les deux points d'entrée PDF de `HandoverPdfBuilder` (rendu réel et échantillon d'aperçu), `getViewLabels()` restant réservée à l'écran d'annotation en direct. **Vérifié en conditions réelles** : PDF régénéré sous une session `en_GB`, libellés de vue toujours en français. **Bug réel signalé par un premier usage humain en production** : un repère ajouté par un technicien via l'écran d'annotation (`front/damagemarker.php`) n'apparaissait jamais sur la vraie fiche PDF (seul l'aperçu, qui re-rend systématiquement à chaque appel, le montrait) — l'ajout/la modification/la suppression d'un repère écrivait bien en base, mais ne déclenchait aucune régénération du PDF non signé déjà généré au moment de la création de la remise, contrairement à `addAccessory()`/`updateObservations()`/`updateVenteDetails()` qui appellent tous `regenerateUnsignedPdf()` après leur propre modification. Nouvelle méthode publique `Remise::refreshDamageAnnotationPdf()` (simple relais vers `regenerateUnsignedPdf()`, restée privée) appelée par les 3 branches de `front/damagemarker.php` après chaque mutation réussie. **Vérifié en conditions réelles** : remise créée, PDF initial sans section (aucun repère), ajout d'un repère puis rappel de cette méthode — le nouveau `Document` stocké (l'ancien est bien purgé) contient la section, l'image et la description, confirmé par relecture visuelle du PDF réellement stocké (pas seulement l'aperçu). **Deuxième bug, signalé juste après par le même usage réel** : même une fois ce correctif en place, la vraie fiche restait vide tant qu'aucun repère n'avait encore été déposé — `getDamageViewsWithMarkers()` (renommée `getDamageViewsForPdf()`) ne remontait, volontairement à l'origine ("document plus compact"), que les vues ayant *déjà* au moins un repère, alors que l'aperçu montre toujours ses 3 vues d'exemple sans condition. Contraire à l'exigence explicite "je veux que le réel ressemble à 100% à l'aperçu" : corrigé pour que les 3 vues de référence soient **toujours** incluses dès que le réglage est actif, repères réels s'il y en a, vierges sinon — comme un schéma d'état des lieux de location de véhicule, présenté par défaut même sans dommage constaté. **Vérifié en conditions réelles** : PDF généré pour une remise sans aucun repère, les 3 vues apparaissent bien, vierges. **Libellés simplifiés** : "Vue arrière — capot fermé"/"Vue de face — écran ouvert" deviennent simplement "Vue arrière"/"Vue de face" (retrait de la précision jugée inutile), sur les deux jeux de libellés (`getViewLabels()` et `getCanonicalViewLabels()`). **Ajout du repère désormais possible depuis la page de signature, pas seulement la fiche admin** : à l'origine, seul un technicien avec le droit `RIGHT_REMISE` UPDATE (via `front/damagemarker.php`, page admin) pouvait déposer un repère — le bénéficiaire lui-même, en train de relire sa fiche avant de signer, ne le pouvait pas. `front/sign.php` gagne les mêmes actions (`add`/`update`/`delete` de repère, plus `update_comment` pour la remarque libre ci-dessous), mais authentifiées - **Fiche de maintenance : sous-système délibérément séparé, pas un type de plus dans `Remise`** — décision actée avec l'utilisateur (deux fois : une fois pour le menu en Phase 1, une fois pour l'architecture de données en Phase 2), motivée par un cycle de vie qui n'a presque rien en commun avec une fiche signée : pas de bénéficiaire, pas de jeton, pas de signature, pas de notification, pas de PDF. Nouvelle classe `Maintenance` (table `glpi_plugin_remise_maintenances`), nouveau droit dédié `Profile::RIGHT_MAINTENANCE` (pas `RIGHT_REMISE` : une organisation peut vouloir ouvrir la maintenance à des techniciens sans accès aux remises/signatures), items de checklist configurables via `MaintenanceChecklistItem` (`CommonDropdown`, même motif qu'`Accessory.php`) stockés dans une simple table de jonction (`glpi_plugin_remise_maintenancechecklistvalues` — à l'origine, la seule PRÉSENCE d'une ligne valait "coché", sans colonne de valeur ; une colonne `value` a depuis été ajoutée pour porter le texte/l'option saisi par les types texte libre/menu déroulant, cf. plus bas). Le détail d'une fiche affiche les points cochés **via une jointure directe** plutôt que de croiser avec la liste des points actuellement actifs : un point désactivé après coup doit rester visible sur un constat historique déjà enregistré.
- **Suite de l'entrée précédente — le PDF et la signature du technicien sont finalement arrivés sur `Maintenance`, sans remettre en cause la séparation d'avec `Remise`** : demande explicite de l'utilisateur (télécharger la fiche en PDF avec le même format que remise/don/vente et le logo de l'entité, plus une signature du technicien optionnelle « comme pour une vente », activable par une case à cocher). - **`MySQL query error: Incorrect date value: '' for column 'sale_date'` à la création d'une fiche de Vente** — signalé par l'utilisateur ("sur la partie vente, j'ai un bug"), reproduit en soumettant le formulaire "Créer une fiche de vente" (`remise_tab.html.twig`) sans remplir le champ `<input type="date" name="sale_date">` (aucun `value` par défaut sur ce champ). **Cause** : `front/remise.form.php` lisait `$_POST['sale_date'] ?? date('Y-m-d')` — l'opérateur `??` ne se déclenche que sur une valeur `null`/absente, jamais sur une chaîne vide ; un `<input type="date">` laissé vide est bien présent dans `$_POST` (valeur `''`, pas absent), donc `??` laissait passer `'sale_date' => ''` directement jusqu'à l'`INSERT` SQL sur `glpi_plugin_remise_ventedetails` (colonne `DATE`), rejeté par MySQL en mode strict avec exactement le message signalé.
